# 0.1.6 祖先任务合并恢复本地验证

日期：2026-10-17。此记录仅证明源码修复与本地回归通过；本任务没有安装或重启现役服务，没有修改使用者状态库、历史失败批次或失败 worktree，也没有执行任何真实客户端构建、签名或发布。

## 根因与实现

基线为 `5059883`、源码版本 `0.1.5`。原 `Worker.integrate` 按任务列表交替 fetch 和 merge；关联修复继承旧任务后，旧 SHA 与当前 main 的冲突会在读取后继解决提交前再次触发。因此，即使修复 SHA 已显式解决冲突并包含全部旧任务，也无法进入准备阶段。

`0.1.6` 先获取每个不同任务的精确远端 SHA，再用 `git merge-base --independent` 选择不被其他任务覆盖的合并头并逐个合并。任务列表、manifest、冻结来源、receipt 及准备后/交付前的逐任务祖先检查保持完整。不存在来源 SHA 仍失败；真正独立的冲突仍保留现场并失败。没有 schema、锁、调度或适配器发布策略变更。

## 新增真实 Git 回归覆盖

- 旧任务和当前 main 修改同一文件，旧批次真实冲突失败；后继修复真实合并两者并显式解决冲突。新关联批次成功后，原任务和修复 SHA 都是冻结提交祖先，文件内容保持明确解决结果。
- 原失败批次完整数据库记录、原 worktree 的 `MERGE_HEAD`、冲突状态和文件字节在恢复后不变；失败批次 resume 仍拒绝。原任务以同一新凭证变为 `recovered`，不可变 SHA 保留。
- 并列独立任务与包含旧任务的后继修复一起合入；独立文件和冲突解决文件都保留。
- 重复 SHA 与已在 main 的任务不丢失审计来源，重复任务不制造额外 merge commit。
- 真实独立冲突保留 `MERGE_HEAD` 和冲突文件，不进入准备、冻结和发布。
- 最后一个任务的精确远端 SHA 缺失时，前面的有效任务也不会先被合并，不进入适配器。
- 中断批次已有部分任务合并时，使用同一 workspace 恢复后仍合入全部 heads。
- prepare 适配器若移除任务祖先，准备后完整祖先核验拒绝冻结和发布。
- 新增成功路径均让适配器在实际发布后丢失一次响应，确认核对恢复且发布次数为 1；原有共用锁串行、不同项目并行、真实租约竞争、失效 owner fencing、更正来源、Unix socket 重启及恢复链回归仍全部通过。
