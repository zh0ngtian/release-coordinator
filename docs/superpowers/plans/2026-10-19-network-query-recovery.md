# 网络查询故障的同批次恢复实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: 使用 superpowers:subagent-driven-development 或 superpowers:executing-plans 按任务执行，并遵循 TDD。

**Goal:** 网络查询暂时失败后保留批次、冻结提交、版本与外部操作 ID，恢复查询后继续验收，避免重新构建。

**Architecture:** 项目适配器仅将可恢复的只读故障输出为结构化结果；核心保留现有 recovering 状态并持久化退避信息，恢复时始终先 check。确定失败继续保留不可变失败记录。用户已在上一轮方案说明后明确要求修复，不重复请求方案确认。

**Tech Stack:** Python、SQLite、原 Unix socket/launchd、原项目适配器 JSON 协议；无新依赖。

## 设计约定

- 兼容既有 `done/result`；新增 `{"done":false,"retryable":{"kind":"transient-read","reason":"脱敏原因"}}`。无此标记的异常继续按旧合同处理，非法或矛盾结果不得当成功。
- retryable 仅表示只读查询/下载无法确认，不能用来盲目重试发布操作。网络未知时不得调用对应 run。
- 同一批次持久化等待阶段、次数、首次失败时间、下次重试时间；默认 5 秒起递增、上限 60 秒并加少量抖动。连续 15 分钟提示 attentionRequired，仍保留可恢复批次。核心不写使用者路径或网络规则。
- 再次查询已成功的阶段只核对实际结果；版本和 frozen SHA 不变，不重复 prepare 或构建。完成/失败的旧历史不改写。
- 写操作报错而对账又暂不可查询时，保留原操作错误，等待查询；只有确认结果后才决定成功或失败，不重复原写操作。
- 调度器尊重下次重试时间；同作用域继续互斥，不同作用域继续运行。服务重启不清空退避。已有 resume 可让非失败批次立即重查；wait 在需要人工关注时可返回状态。
- 项目适配器对 EOF、超时、连接/DNS、408/429/5xx 等只读故障分类；鉴权、构建失败、来源/散列不匹配不冒充网络等待。保留原 CI run/attempt 与下载检查点。

## 验证边界

所有外部故障验收使用独立临时状态库和本地假服务，不创建真实 App Release、版本预留或业务会话。最后验证现役服务安装状态；不把模拟故障验收说成新的 App 渠道发布。
